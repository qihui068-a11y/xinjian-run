## 0. 结论

**这一版确实在改，而且改对了大部分。** 整改记录的 15 条声明里，14 条经复核成立；**1 条不成立**（M3 只覆盖了三分之一入口），另发现 **3 个新缺陷** + **1 个测试有效性问题**。

| 判定 | 数量 |
|---|---:|
| 声称已修且复核成立 | 14 |
| 声称已修但**实际不完整** | 1（M3） |

**总体判断**：0.7.9 比 0.7.8 明显更稳，H1 的核心洞（陌生人一条文本锁死会话）已经堵死，且改动没有引入回归（官方 58 项全绿）。但「删除即删图」这条做了却没做全，还有一个新引入的 UI 卡死。**建议修完 N1/N3 再发版。**

## 2. 我上一轮的错误，先更正

我在第一轮把 **M1「控制指令无回执」** 记为中危，复核时用 4.3 秒窗口测量，误判为「仍未重发」。实际重发是 **4s 超时 + 0.8s 退避**，第二次发送在 4.81s 才发生。**M1 是修好了的**，是我测早了。特此更正。

另外，整改记录第 1 条异议是对的：我原建议「控制指令只接受已通过验证的好友」对「同意」不适用——同意本来就发生在成为好友之前。他们的替代方案（精确匹配 + 必须处于 `waiting`）强度等价且不破坏流程，实测通过。这条我接受。

## 3. 本轮新发现

### N1 · 三条删除路径里只有一条删图（中危，隐私）

| 项 | 内容 |
|---|---|
| 位置 | `chat.js:238-239`（通讯录）、`chat.js:771-772`（会话设置）、`chat.js:431-432`（终止后三选一） |
| 定性 | **整改记录 M3「已修」与实现不符** |

**现象**：删图逻辑写在 `Lan.dropContact()` 里（`lan.js:296-305`），但三个用户入口有两个是条件调用：

```js
/* chat.js:238 通讯录 */
if (Lan.running()) Lan.dropContact(f.id);
else Pigeon.deleteFriend(f.id);          // ← 局域网没开就不删图

/* chat.js:771 会话设置 */
if (Lan.running()) Lan.dropContact(peer);
else Pigeon.deleteFriend(peer);          // ← 同上

/* chat.js:431 终止后选「删除通讯」/「备份后删除」 */
Pigeon.deleteFriend(s.peer);             // ← 完全不删图
```

**动态复现**：

```
A 终止后选「删除通讯」:: 实际删盘=[] 会话还在=false
（另一次：局域网关闭时在会话设置里删除，删盘=[]，会话已删）
```

**影响**：用户以为删掉了，图片仍在 `media/` 里且可通过 `/media/<name>` 打开；与「删除」语义直接冲突，也占着磁盘。

**建议**：把图片清理下沉到 `Pigeon.deleteFriend`（让它通过 `Bridge`/`Lan` 拿到 media 删除能力），或抽一个 `Pigeon.dropContact(peer)` 统一封装；不要在三个视图里各写一遍分支。

### N2 · 被屏蔽的好友仍能触发「终止通讯」（中低）

| 项 | 内容 |
|---|---|
| 位置 | `lan.js:70-75`（控制分支在 `Pigeon.receiveLan` 的屏蔽判断之前） |

**现象**：文本消息的屏蔽判断在 `Pigeon.receiveLan` 里（`data.js:127`），但控制指令在 `lan.js` 里先行处理，没有经过屏蔽过滤。好友被屏蔽后，对方发 `\u0002已终止通讯` 依然生效。

**动态复现**：`H1 被屏蔽的好友仍可终止会话 :: terminated=true（期望 false）`

**影响**：屏蔽的语义是「这个人我不要了」，但对方仍能锁死这个会话（输入框禁用、弹三选一）。配合未修的 H2（身份可伪造），任何知道好友 id 的设备都能做到。

**建议**：控制分支最前面加一句 `if (Pigeon.blocked(event.id)) return;`。一行的事。

### N3 · 图片发送中关掉局域网，消息永远停在「发送中…」（中低，新引入）

| 项 | 内容 |
|---|---|
| 位置 | `lan.js:228-246`（`fail()` 的 epoch 分支） |

**现象**：M7 的修复在 `fail()` 里加了 epoch 检查，但**在 epoch 不匹配时直接 `return finish()`，跳过了 `Pigeon.delivery(session.id, mid, false)`**。于是关网瞬间在途的图片永远不会被标记失败。

```js
function fail(permanent) {
  if (timer) { clearTimeout(timer); timer = null; }
  if (myEpoch !== epoch) { delete waiters[mid]; return finish(); }   // ← 没有落 failed
  ...
  Pigeon.delivery(session.id, mid, false);
}
```

**动态复现**：

```
B 发送中={"shared":true,"delivery":"pending"}
B 关网 26.5 秒后 delivery=pending（期望 failed）
```

**影响**：气泡永远显示「发送中…」，没有「重发」按钮（只有 `failed` 才出现），用户既不知道失败也无法重试。文本消息不受影响（它们走 `pending` 表，关网时被批量标 failed），**只有图片这一条路径是坏的**。

**建议**：epoch 不匹配时也要落一次 `Pigeon.delivery(session.id, mid, false)` 再收尾。

### N4 · 新测试绕过了真实入口，所以 N1 没被测出来（过程问题）

| 项 | 内容 |
|---|---|
| 位置 | `tests/lan.cjs:467-492`（`Deleting a contact removes its image files too`） |

**现象**：这条测试直接调用 `w.Lan.dropContact(PEER)`，而不是走「通讯录/会话设置里点删除」。它验证的是函数本身，不是用户路径，因此当三个入口里有两条不删图时，测试依然是绿的。

**影响**：这不是代码 bug，是**护栏失效**——恰好是这类测试最危险的地方：它让整改看起来完成了。

**建议**：补一条走 UI 的用例（通讯录滑动 → 删除 → 确认），并覆盖「局域网关闭」这个前置条件。

## 4. 残余风险（已接受，但需要写清楚）

### 4.1 H2 / H4 未修

身份仍可伪造、链路仍明文。这不是「忘了」，是明确排到 P2 的取舍，我认同在当前阶段（可信局域网）可以接受。但需要把话说全：

- H2 让 N2 从「熟人骚扰」升级为「同网任何人冒充好友终止你的会话」；
- H4 让中间人可以伪造 ack，把「已送达」变成一句空话；
- 这两条不解决，**鸽屋就不能进公共 WiFi**（咖啡厅、学校、共享办公）——这一点建议写进产品说明，而不只是代码注释。

### 4.2 M2 的「落盘后立即删」是尽力而为

删盘动作发生在 JS 收到 `img` 事件时。如果那一刻应用在后台/被杀（`onStop` 会关传输，事件不会到 JS），文件已经写进 `media/` 且没人删。也就是说：**屏蔽期间对方发的图，可能仍留在盘上**。彻底解决确实要把 blocked 下推原生（记录里的异议 2 说得对，两条路都有两个真源的问题，但可以用「原生只存一个 blocked 的 id 集合」这种单向同步来规避）。

### 4.3 H3 的内存问题解决了，可用性问题还在

8 个槽位 + 30s TTL 挡住了内存爆炸，但：

- `prune()` 只在新块到达时执行，槽位被 8 个垃圾 `mid` 占住后，**正常图片 30 秒内收不到**（发送方 15s 超时 → 失败 → 重试，仍失败）；
- 逐来源限制按 `xj-id` 计，而 id 可换（H2），换 8 个 id 就能占满；
- 没有 LRU：先到的半张图会一直占到 TTL 到期。

**建议**：表满时淘汰最旧的未完成条目（而不是直接丢弃新块），并给 `images` 加一个全局字节上限（如 4MB）。
