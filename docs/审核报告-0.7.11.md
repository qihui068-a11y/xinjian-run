## 2. 同源性核验（本轮新增检查）

### 2.1 源码 → APK：逐条目比对

用 `apktool b` 把源码 zip 里的 `modified/` 原样回编译，与发布 APK 比对每个条目的 SHA-256：

```
发布 APK 条目: 45   重编译条目: 45
只在发布包: （空）
只在重编译: （空）
内容不同: 0
  classes.dex          发布=51D73060C311A0F1 重建=51D73060C311A0F1 一致=True
  resources.arsc       发布=CCD5484248CF28DA 重建=CCD5484248CF28DA 一致=True
  AndroidManifest.xml  发布=D21BC07BFF8AA280 重建=D21BC07BFF8AA280 一致=True
```

**结论：发布包就是这份源码编译出来的，没有夹带、没有手改、没有版本错配。**

### 2.2 Java 源码 → smali：逐字节重建

再用 `native/lan/build.py` 从 `native/` 的 Java 源码重新生成 smali，与源码仓库里已提交的 smali 比对：

```
Updated 16 lan smali classes
一致: 16   不一致: 0
```

两级拼起来就是完整链路：**Java 源码 → smali → classes.dex → APK**，每一级都逐字节可复现。这意味着以后 native 改动的 diff 只会是真实改动。

## 3. 逐条复核

### N5 · 备份引用随即被删的图片名 —— 成立

`data.js` 的 `chatText` 改为：

```js
var hasImage = s.msgs.some(function (m) { return m.kind === 'image'; });
if (hasImage) out.push('# 注：本备份只含文字，图片不包含在内');
...
var body = m.kind === 'image' ? '[图片]（未包含在备份中）' : (m.text || '');
```

**动态复现**：

```
备份正文是否引用图片文件名 = false   （0.7.10 为 true）
备份后是否删除该图片        = ["xj-b.jpg"]
```

现在「备份成功」与「备份里有什么」是一致的：正文不再指向被删掉的文件。

我认同选方案 2 的理由——跳过删图会让「删除」变成半删，与 M3 的初衷冲突；图片一并导出是功能项，不该混进整改。**取舍写进了正文，用户看得见**，这是三类方案里唯一「说到的和做到的完全一致」的。

小提示：图片占位丢掉了「是哪张图」的信息，只剩时间戳能定位。纯文本备份里这可以接受；若将来要做图片备份，需要新的导出格式（zip 或 sidecar 目录），不建议在 txt 里塞 base64。

### R1 · 淘汰可被利用打断他人传输 —— 成立

```java
private static final long EVICT_MIN_AGE_MS = 5000L;

while (images.size() >= MAX_IMAGES) { if (!evictOldest()) return; }

private boolean evictOldest() {
    long now = System.currentTimeMillis();
    ...
    if (now - started < EVICT_MIN_AGE_MS) continue;   // 新鲜条目不动
    ...
    if (oldest == null) return false;                 // 全是新鲜的 → 拒收新块
    images.remove(oldest);
    return true;
}
```

两层保护都在：年龄下限挡住「瞬间挤掉」，返回值让「全都是新鲜条目」时改为拒收。反编译 APK 的 smali 也确认了同样的结构与 `0x1388`（5000）常量，**源码与产物一致**。

副作用评估：表满且全新鲜时，新图会被拒收，最多等 5 秒后自然可淘汰。JS 侧有自动重试，能自愈。可接受。
