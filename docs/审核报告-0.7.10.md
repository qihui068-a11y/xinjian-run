### 关键改动的实现质量

`Pigeon.deleteFriend` 现在是唯一的删除收口（`data.js:353-367`）：先取 `imageNames`，再删好友与会话，最后触发删盘钩子。三个入口（通讯录 `chat.js:238`、会话设置 `chat.js:771`、终止弹窗 `chat.js:431`）无论 LAN 开关都走同一条路，**上一轮的分支漏写问题从结构上消失了**，不是又补了一个 if。

`inflight` 表（`lan.js:29`）记录 `mid → 会话 id`，`setState(false)` 时逐个落 `failed`（`lan.js:50-53`），成功/失败/epoch 失效三条路径都会清表。**没有泄漏点**。

## 2. 本轮新发现

### N5 · 「备份后删除」：备份文本引用图片文件名，随后图片被删（中低）

| 项 | 内容 |
|---|---|
| 位置 | `chat.js:431-434`（`termCheck` 的 backup 分支）、`data.js:260-275`（`chatText`）、`data.js:353`（`deleteFriend` 删盘） |

**现象**：选「备份通讯后删除」时，`backupChat()` 导出的正文里图片写成 `[图片 xj-b.jpg]`，紧接着 `Pigeon.deleteFriend` 把 `xj-b.jpg` 从 `media/` 删掉。备份留下了文件名，文件没了。

**动态复现**：

```
备份正文是否引用图片文件名 = true
备份后是否删除该图片        = ["xj-b.jpg"]
```

**性质**：这是 N1 修复带来的**副作用**——0.7.9 之前删会话不删图，备份里的文件名还能对上；现在删图了，备份就成了半份。

**影响**：用户以为「备份过了」，实际图片全丢，只剩一串文件名。属于「备份承诺与实现不一致」，比单纯丢图更伤信任。

**建议**（任选其一）：

1. `backup` 分支跳过删图（保留文件，代价是占空间）；
2. `chatText` 导出时把图片名去掉，并在正文注明「图片不包含在备份中」；
3. 备份时把图片一并导出（工作量大，可排后）。

> 我倾向 1 或 2。**当前状态是最糟的组合**：既给了文件名，又把文件删了。

## 3. 残余提示（不阻塞发版）

### R1 · 淘汰策略可被利用来打断他人传输

`evictOldest()` 解决了「垃圾 mid 占位导致正常图片进不来」，但方向反过来变成了「谁都能把别人的半张图挤掉」：任何设备连续开新 `mid`，就能反复淘汰他人正在接收的图片，让对方每次都在中途失败。

内存是安全的（4MB 上限＋8 条目），损失是**可用性**与**白费带宽**。

建议：淘汰时加一道年龄下限（例如只淘汰已存活 > 5s 的条目），全部是新鲜条目时改为拒绝新条目——这样既不会被长期占位，也不会被瞬间挤掉。

### R2 · `apktool.yml` 的 `apkFileName` 仍是 `信笺_0.7.2_运行版.apk`

版本号已经到 0.7.10（versionCode 17），但这个字段还停在 0.7.2。不影响构建，只是回编译日志里会印出错误的源包名，容易误导排查。顺手改掉即可。
