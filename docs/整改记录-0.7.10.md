# 审核报告（第二轮）整改记录 · 0.7.9 → 0.7.10

对照 `docs/审核报告-0.7.9.md`。**N1/N2/N3/N4 全部修复，4.3 的淘汰策略也补了**；4.1/4.2 维持原判断。

## 本轮修复

| 编号 | 状态 | 做法 |
|---|---|---|
| N1 三条删除路径只有一条删图 | **已修** | 图片清理下沉到 `Pigeon.deleteFriend`（通过 `window.__xjDropMedia` 钩子删盘），三个入口全部走同一函数；`Lan.dropContact` 只负责发终止信号 |
| N2 被屏蔽的好友仍能终止 | **已修** | 控制分支最前面加 `if (Pigeon.blocked(id)) return;` |
| N3 关网后图片停在「发送中」 | **已修** | epoch 失效分支补落 `Pigeon.delivery(..., false)`；另加 `inflight` 表，关网瞬间把在途图片一次性结算为失败 |
| N4 测试绕过真实入口 | **已修** | 新增两条 UI 路径用例：通讯录滑动删除（局域网关闭）、终止后选「删除通讯」，都断言 `deleteMedia` 被调用 |
| 4.3 表满不淘汰 | **已修** | 表满时淘汰最早开始的半张图（而不是挡住新块）；另加 4MB 全局字节上限 |

## 维持不改

- **4.1 H2/H4**：需要双端一起升级协议，仍排 P2。
- **4.2 blocked 下推原生**：认同「原生只存一个 blocked id 集合」这条路，但它需要新增一条 JS→原生的单向同步通道（blocked 变更时推送），
  属于协议/接口改动，放到下一轮和 H2 一起做。当前「落盘后立即删」是尽力而为，报告里说的「后台被杀时可能残留」成立。
- **4.3 的按来源限制**：依赖身份可信（H2），现在按 `xj-id` 计数确实可绕过。

## 对报告的两点回应

1. **M3「不成立」我接受**：上一版整改记录写的是「删联系人时按会话图片名逐个删」，但实现只落在 `Lan.dropContact`，
   而通讯录/会话设置两个入口在「局域网关闭」时会走 `Pigeon.deleteFriend` 分支，确实漏了。这是我记录写过头，不是报告看错。
2. **M1 的更正我收到了**：4s 超时 + 0.8s 退避，第二次发送在 4.81s，审核用 4.3s 窗口测早了。这条不用改代码。
