## 2. 文案准确性（逐条对照代码事实）

| 文案断言 | 代码事实 | 判定 |

| 「不做身份校验：同一个网络里的设备可以自称成任何人，也可以冒充你的好友」 | `LanTransport.validPeer()` 只校验 `xj-[0-9a-f]{12}` 格式；`acceptMessage()` 信任 `hello.id`；无签名无密钥 | **准确** |

措辞上有一处可以更严谨：**「手机热点」要加限定**——如果热点是共享给别人的（公共热点、临时给别人连），风险和咖啡厅 WiFi 是同一类。建议改成「自己独占的手机热点」。

整体判断：这段话没有为了好读而弱化风险，也没有为了免责而夸张——**「这一条不是『以后再说』，是当前协议的硬边界」这句写得尤其好**，把「暂时」和「永远」分开了。

## 3. 本轮主要发现：位置与意图不一致（P1）

整改记录写得很清楚：「这条边界影响的是**用户在哪里打开它**」。但实现放在「小家 → 关于」：

```
小家 → 关于 → 往下翻 → 「鸽屋的使用边界」（第 2 个字段）
```

**实测确认**：

```
关于页含「鸽屋的使用边界」= true
含「不做身份校验」      = true
鸽屋页是否出现「可信/公共 WiFi」提示 = false
局域网按钮文案 = "局域网"
```

也就是说：用户坐在咖啡厅里，点进鸽屋、点「局域网」，**整个过程看不到一个字的风险提示**；而愿意翻到「关于」的人，本来就不是最需要被提醒的那批。

**建议（二选一，成本都很低）**：

1. **首次开启局域网时弹一次确认**（记住选择，之后不再弹）——把提示放在决策点上；
2. **鸽屋页的局域网按钮下方常驻一行小字**：`仅限可信网络 · 明文`，点它跳到「关于」的完整说明。

我倾向 1 + 2 组合：1 保证看过，2 保证随时能查。

## 6. 如果你们要开 H2/H4，我建议先定这三件事

记录里说需要先定三件事，我把它们补全，并给出我的倾向：

### ① 身份模型：设备密钥 vs 好友间共享密钥

- **A（我倾向）每设备一对长期密钥**（Ed25519 或 P-256），加好友时交换公钥并把公钥绑到 `xj-id`。好处：一台设备对多个好友只维护一份身份；将来做群聊也成立。
- B 每对好友协商一个对称密钥（ECDH）。实现更简单，但好友一多就是 N 份密钥，群聊要再设计。

### ② 兼容策略：硬切 vs 软降级

- **A（我倾向）硬切**：v2 只与 v2 通信，遇到 v1 设备在列表里显示「对方版本过旧」。边界干净，用户不会以为自己「加密着聊」。
- B 软降级：v1 仍可明文聊，但 UI 标注「不安全」。保留兼容，代价是给自己留了一条能降级的路——降级攻击的教科书入口。

### ③ 完整性范围与重放

- **A（我倾向）文本与控制帧全签；图片块只签头部**（`mid/seq/total/size`）**+ 整图校验和**。每块都签会让 CPU 和带宽翻倍，收益很小（图片内容最终由整图校验和兜底）。
- 重放：`mid` + 单调 `seq` + 5 分钟时间窗 + 去重表。现有 `mid` 去重可以复用，加时间窗即可。

> 这三条定下来，H2/H4 的实现路径就唯一了：密钥交换（①）+ 版本协商（②）+ 帧签名（③）。剩下的都是工程量。
