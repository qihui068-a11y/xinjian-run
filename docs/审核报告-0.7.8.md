## 0. 摘要

鸽屋这一版把「能不能聊」做完整了：发现、验证、通讯录、会话设置、图片都有闭环，代码分层清楚，错误路径也考虑了降级（没有原生桥时提示而不是崩溃）。**工程质量本身是合格的。**

问题集中在两处：**协议没有身份与完整性**，以及**边界条件没有兜底**。前者导致同网任何设备可以冒充、可以伪造「同意/终止」这类控制指令；后者导致内存、磁盘、localStorage 这些有限资源都能被对端或自己撑爆。

| 级别 | 数量 | 是否可以发版 |
|---|---:|---|
| 高危 | 4 | 必须先修 |
| 中危 | 8 | 发布前应修 |
| 低危 | 9 | 可以排到下一轮 |

**最需要立刻处理的三条**：

1. `\u0002` 终止指令无来源校验 —— 同网任何设备发一条文本就能把你的会话锁死（已动态复现）。
2. 图片分块装配没有数量上限 —— 一条 TCP 连接就能把接收方内存吃光。
3. 身份 `xj-xxxxxxxxxxxx` 可以随意伪造 —— 冒充好友发消息、发图在协议层没有任何门槛。

## 2. 协议与状态机总览（审核基线）

```
发现（UDP 45789，广播 255.255.255.255，每 3s，11s 判离线，上限 128 台）
   ↓
TCP 45790 短连接，握手 hello{v,t,id,nick,tcp}
   ↓
   ├─ 文本帧 {t:'msg', mid, from, to, text, ts}  → 回 ack{mid}
   ├─ 图片帧 {t:'img', mid, seq, total, name, w, h, data} → 每块回 ack{mid,seq}
   └─ 控制信号：复用文本通道，首字符 \u0001=同意,\u0002=终止
```

会话状态（`Pigeon`）：`waiting`（我发过、等对方回）→ `friend`；陌生人消息不进会话，进 `requests`；`blocked` / `terminated` / `ignored` 为终态标记。

**这里有个结构性判断**：把「控制信号」塞进文本通道首字符，是这一版最省事、也最危险的设计。它让协议在不解码的前提下无法区分「用户说的话」和「系统指令」（见 H1）。

## 3. 高危问题（4 项）

### H1 · 控制指令无来源校验：一条文本即可锁死或冒充「同意」

| 项 | 内容 |
|---|---|
| 位置 | `lan.js:65-77`（接收侧）、`lan.js:249-265`（发送侧） |
| 级别 | 高危 |

**现象**：`__xjLan` 收到文本后，先看首字符：`\u0002` → `Pigeon.terminate(peer)`；`\u0001` → 若本地 `waiting` 则直接 `Pigeon.accept(peer)`。两者都只校验了 `event.id` 格式，没有校验「这条指令是不是对方真的点了按钮」。

**证据（动态复现）**：

```
P2 任意对端一条 \u0002 即可锁死会话  :: terminated=true 输入框禁用=true 三选一弹出=true
P3 一条 \u0001 文本即被视为好友通过（无任何校验）  :: 之前是好友=false 之后是好友=true
```

**影响**：

- 同一 WiFi 下任何设备（包括**尚未通过验证**的陌生人）只要能发消息，就能让某个会话进入 `terminated`，输入框锁死、每次进入都弹「对方已终止通讯」。
- `\u0001` 可以把「我主动加的人」直接转正，绕过验证流程。
- 结合 H2（身份可伪造），攻击者不需要真的与你是好友。

**建议**：控制指令不要复用文本通道。哪怕不加密码学，也应满足：① 只接受**已通过验证**的好友发来的控制帧；② 指令带 `mid` 并回执；③ 优先级上，终止应作为**可撤销的状态**而不是单向开关（见 M4）。

### H2 · 身份无任何认证，`xj-id` 可随意伪造

| 项 | 内容 |
|---|---|
| 位置 | `LanTransport.java:180-203`（announce/observe）、`:313-326`（收文本） |
| 级别 | 高危 |

**现象**：设备身份就是握手包里的一个字符串 `xj-[0-9a-f]{12}`，广播和 TCP 握手都不带任何证明。`observe()` 只看格式，`acceptMessage()` 只要求 `from == hello.id`，也就是「自称是谁就是谁」。

**影响**：攻击者广播一条 `{id: 受害者的 xj-id}` 就能在附近列表里顶替对方；给好友发消息时可以带对方的 id，收件方会把它记到「好友」名下。之后 H1 的两条指令也就跟着合法了。

**建议**：最小可行方案是首次加好友时交换一对长期公钥（或至少一个共享随机串），之后每条消息带 HMAC。局域网内做这件事的成本约两天，比上服务器便宜得多。

### H3 · 图片分块装配没有数量上限，可被一条连接打爆内存

| 项 | 内容 |
|---|---|
| 位置 | `LanTransport.java:329-364`（`acceptChunk`）、`:62`（`images` 表） |
| 级别 | 高危 |

**现象**：每遇到一个新 `mid` 就在 `images` 里建一个 `Incoming` 并保留已收块（每块最多 9000 字节）。`images` **没有条目上限、没有超时清理、没有按来源配额**。`close()` 才会清空。

**影响**：一条 TCP 连接连续发 10000 个不同 `mid`、每个只发 1 块，就能让接收方保留约 90 MB 的 `byte[]`，且不会被回收。128 台设备的上限只约束了 `peers`，不约束图片装配表。

**建议**：给 `images` 加三个硬约束——条目上限（如 8）、单张未完成时长（如 30s 清理）、每来源同时在传数量（如 1）。

### H4 · 明文传输，无完整性校验

| 项 | 内容 |
|---|---|
| 位置 | 全链路（`LanTransport` 全程 `Socket` 裸传 JSON） |
| 级别 | 高危（隐私）/ 已知限制 |

**现象**：文本、图片、控制指令都是明文；`ack` 没有签名；`ts` 是发送方自报。

**影响**：同网段抓包即可还原聊天内容与图片；中间人可以改写文本、伪造 ack（让发送方显示「已送达」而实际没收到）。

**建议**：与 H2 一起做（公钥交换 + 每帧 HMAC），一次解决认证与完整性；加密可选，但至少要让「篡改」可被发现。

## 4. 中危问题（8 项）

### M1 · 控制指令没有回执与重发，好友关系可能永久停在「等待回复」

- 位置：`lan.js:249-265`；`data.js:298-303`。
- 现象：`accept()` / `dropContact()` 用 `bridge.send(peer, newMid(), ...)` 发一条控制文本，**没有加入 `pending` 表**，因此没有 delivery 回执、没有重试；发送时对端不在线就静默丢失。
- 影响：A 点了「同意」，B 那边仍显示「验证消息已发出，等对方回复」；B 再发消息又会走一遍验证。双方认知不一致，且无法自愈。
- 建议：控制帧带 mid 并复用文本的 ack/重试；或把「我同意了」做成幂等的状态同步（对方下次上线时重发）。

### M2 · 被屏蔽/非好友仍可把图片写进磁盘

- 位置：`LanTransport.java:329-381`（先 `store()` 再 `emit`）；`data.js:129-143`（JS 侧才判 blocked）。
- 现象：原生收到图片块、收齐、写盘、落盘成功后**才**通知 JS；JS 的 `receiveImage` 对 blocked 返回 false。
- 影响：屏蔽只是「不显示」，对方的图片仍然落到 `media/`，可以无限灌（每张 ≤2MB，无总量控制），也可以被 `/media/<name>` 直接打开。屏蔽在存储层面不生效。
- 建议：把 blocked 列表下推到原生（或先 emit 一个 `img-offer` 由 JS 决定是否接收），并在原生侧加配额。

### M3 · 删除联系人/会话不删图片文件，隐私残留

- 位置：`data.js:317-324`（`deleteFriend` 只删 friend + session）；全仓无媒体清理逻辑。
- 现象：`media/xj-<mid>.jpg` 只有在卸载应用时才消失。
- 影响：用户执行「删除」后，图片仍在设备上，且可通过 `/media/<name>` 访问；与「删除」的语义不符。
- 建议：删除会话时按 `mid` 关联清理 `media/xj-<mid>.jpg`；或在设置里提供「清理聊天图片」。

### M4 · 「终止通讯 → 保留」使会话永久锁死，且每次进入都弹窗

- 位置：`chat.js:421-435`（`termCheck`）、`:489-497`（`paintLock`）；`data.js:212-218`（`terminate` 只置位，无清除入口）。
- 证据：

```
P8 终止后选「保留」，会话永久锁死且每次进入都弹窗
   :: 首次弹=true 再进弹=true 仍锁=true terminated=true
```

- 影响：用户选「保留」的本意是**留下记录**，结果得到一个永远不能输入、每次打开都弹三选一的会话。`termShown` 是视图级变量，重进即失效。
- 建议：`terminated` 应区分「对方已终止」与「我已确认」，确认后清除标记改为只读+可重新发起；弹窗只出现一次。

### M5 · 图片消息不参与会话列表摘要

- 位置：`chat.js:56`（`var last = s.msgs[...].text`）、`:69`（`esc(last || '还没有消息')`）。
- 证据：`P1 图片消息后会话列表摘要 :: 实际显示="局域网 · 还没有消息"`。
- 影响：只发过图片的会话在列表里看起来像从没聊过；用户会以为发送失败。
- 建议：摘要按 `kind` 分支，图片显示「[图片]」。

### M6 · localStorage 写满时静默失败，且请求表可被灌满

- 位置：`data.js:62`（`save()` 的 `try/catch` 吞掉异常）；`data.js:175-187`（`addRequest` 无上限）。
- 现象：任何 TCP 连接都能用不同 `xj-id` 反复发消息 → 每个 id 生成一条 request；条目只增不减，直到超过 WebView 的 localStorage 配额（通常 5–10 MB）。一旦写满，`save()` 静默失败，此后的**所有**消息、好友变更都不再落盘。
- 影响：不是「脏数据」，是**静默数据丢失**——界面照常显示，重启后消失。
- 建议：① `save()` 失败要有用户可见提示；② 请求表加上限（如 200 条，溢出丢最旧）；③ 会话消息按条数/字节做上限或分表。

### M7 · 关闭局域网时图片队列的竞态

- 位置：`lan.js:32-45`（`setState(false)` 清 `queue`、置 `busy=false`、删 `waiters`）与 `:183-246`（`pump`/`run` 里还有 25s 定时器）。
- 现象：关网瞬间若有图片在传，`busy` 被强制清零但旧任务的 `finish()` 仍在跑，之后 `pump()` 可能被新旧两条链路同时触发；被删掉的 waiter 在 25s 后触发 `fail()`，把任务 `unshift` 回已清空的队列，重新开网后可能继续发送。
- 影响：「同一时刻只传一张」的保证会被打破；对已断开的会话重发。
- 建议：给每个任务一个 epoch/token，`setState(false)` 时递增，任务回调发现 token 过期即丢弃。

### M8 · 连接池与端口无速率限制

- 位置：`LanTransport.java:65-66`（recv 4 线程 / 12 队列）、`:256-271`（accept）。
- 现象：同时 16 个连接即可占满接收池，第 17 个直接关闭；UDP 广播也没有频率保护。
- 影响：同网设备一条循环脚本就能让鸽屋「时好时坏」，且用户看到的是「对方离线」。
- 建议：按来源 IP 限速、加连接空闲超时、UDP 包按来源做窗口计数。

2. **网络环境**：部分路由/热点下 `255.255.255.255` 广播可能不出网卡；AP 隔离、双频分离、IPv6-only 场景未测。
3. **性能**：1000 条消息的列表渲染、连续发 20 张图的队列行为未做压测。
4. **电量**：3 秒一次广播 + MulticastLock 的功耗未测。
5. **无障碍/大字体**：本次未审。
